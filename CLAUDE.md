# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

3Denlive is a stereoscopic (3D) photo/video montage desktop app: plain Java + SWT GUI. There is no Maven/Gradle; everything is built with `javac`/`jar` and shell scripts. The IDE is VS Code, configured in `.vscode/`:
- `settings.json` defines the project as an unmanaged folder: `src` → `bin`, plus `distrib/*.jar` and the Linux SWT for compiling.
- `launch.json` has one run configuration per platform, with that platform's SWT and `cwd` set to `distrib/`.
- `tasks.json` runs the scripts.

Don't reintroduce Eclipse `.project`/`.classpath` files. There are no tests and no linter.

## Build & run

The main class is `com.cubaix.TDenlive.TDenlive`. The code is compiled with `--release 27`, so JDK/JRE 27+ is required.

Each configuration has a folder `distrib/<config>/` with its SWT jar, the natives extracted into `lib/`, and a launcher. The configurations are `Linux`, `PPC64le`, `Win-x64`, `MacIntel` (x86_64) and `MacSilicon` (arm64).
- All folders use SWT 3.135.0 (natives `*-4974r10`) from Maven Central `org.eclipse.platform:org.eclipse.swt.<ws>.<os>.<arch>`.
- An x86_64 SWT fails to load on an arm64 JVM with `UnsatisfiedLinkError: incompatible architecture`.

Dev build into `bin/` (gitignored). Any platform's SWT jar works for compiling:

```sh
javac --release 27 -encoding UTF-8 -d bin -cp "distrib/*:distrib/Linux/swt.jar" $(find src -name '*.java')
```

Dev run: start from `distrib/`, with `src/` on the classpath. The language XML files, images and fonts are loaded with `getResourceAsStream` from `src/`, and `javac` doesn't copy them into `bin/`. `ffmpeg/`, `lumas/` and `frames/` are loaded relative to the working directory.

`./run_3De.sh [-n] [config] [-- app args]` does both steps: it recompiles `bin/` from scratch and runs the app with the config detected from `uname`. `-n` skips the compilation. It runs on macOS and Linux only. The app's standard and error outputs go to `log/3De.log` (gitignored, replaced at each run). The app accepts a project file as its only argument (`./run_3De.sh -- my.3De`). By hand:

```sh
cd distrib && java -XstartOnFirstThread -Xmx4G --enable-native-access=ALL-UNNAMED -cp "../bin:../src:*:MacSilicon/swt.jar" -Djava.library.path=MacSilicon/lib com.cubaix.TDenlive.TDenlive
```

On Linux, drop `-XstartOnFirstThread`, use the `Linux/` jar and libs, and set `GTK_OVERLAY_SCROLLING=0`. The README has the per-platform variants.

`./Install-Dev.sh` downloads two kinds of binaries into gitignored folders:
- ffmpeg into `distrib/ffmpeg/`. The binaries are not in Git or in the jar because they are 60 to 180 MB each. The files are named `ffmpeg-<os.arch><suffix>`: `ffmpeg-amd64`, `ffmpeg-amd64.exe`, `ffmpeg-x86_64-osx`, `ffmpeg-aarch64-osx`. `SOURCES.txt` records where each one came from.
- A Java 27 JRE per config into `JVMs/<config>/`: Temurin, or Azul Zulu for MacIntel because Temurin has no macOS x64 build.

Its options are config arguments, `--ffmpeg-only` or `--jvm-only`, and `-f` to re-download the latest releases.

`./build_delivery.sh [config...]` builds the deliveries:
- It compiles into `delivery/build/`, copying the resources next to the classes, then builds the jar.
- Each config gets a self-contained `delivery/3Denlive<config>.tar.gz`, except Windows, which gets a `.zip`. The archive contains the jars, SWT, `lumas/`, `frames/`, the platform's `ffmpeg/`, `jre/` and the launcher.
- The launchers (`distrib/<config>/3Denlive.sh`, `Win-x64/3Denlive.bat`) use `./jre` when it is present, and the system java otherwise.
- PPC64le has no bundled ffmpeg and uses the system one.

`src/demo/DemoLogo.zip` goes into the jar like the other resources: at startup, `TDenlive.installDemo()` unzips it into `~/3Denlive/` if `DemoLogo/DemoLogo.3De` does not exist (the files already there are kept).

`distrib/3Denlive.jar` is tracked in Git but not regenerated by any script.

## Version

The version lives in `src/com/cubaix/TDenlive/VERSION.txt` (one line, `X.Y.Z`). `TDenlive.TDeVersion` reads it with `getResourceAsStream`, and `build_delivery.sh` reads it for its output. **After any code change, increment the last number (Z) by 1**, once per set of changes, not once per file.

## Architecture

All code lives in `com.cubaix.TDenlive`, with a vendored Nebula `TableCombo` widget under `org.eclipse.nebula`.

- **`TDenlive`** is the app root. A single instance is passed to almost every constructor as `tde`/`aTDe`, and it holds `config` (`TDConfig`), `gui` (`TDeGUI`), `mediaList`, `timeLineStack` and `selected`. It also writes and reads the project file.
- **Persistence**: projects (`<3De>…</3De>`) and the user config (`~/3Denlive/3De.conf`) are hand-built XML. They are written by appending to a `StringBuffer` in each class's `saveProject(StringBuffer)`. They are read with the custom `xml.XmlMinimalParser`, which turns the file into a flat `Vector<XmlObject>`. Each class's `openProject(Vector<XmlObject> aOs, int o)` consumes tags from index `o` and returns the new index; a tag's text is in `aOs.elementAt(++o).text`. Follow this cursor pattern for any new persisted field, and keep save and load symmetric.
- **Media model (`medias/`)**: `Media` (abstract, extends `GUI.Drawable`) has these subclasses:
  - `StereoImage`, with `StereoMovie`, `StereoSvg` and `ColorBck` extending it. `utils.MpoReader` handles MPO stereo photos.
  - `Clip`, a placement of a media on a timeline. It owns an ordered `processors` list and links to its twin clips.
  - `VideoTimeLine` and `AudioTimeLine`.
  - `TimeLineStack`, which composes the timelines.
  - Timeline clips draw a film strip: `Media.getThumbAwtAt(time)`. For `StereoMovie` it comes from `ffmpeg.VideoThumbnailer` (one background ffmpeg run per video, one video at a time); the single `buildThumb()` image is only the media list thumbnail and is no longer rebuilt at each frame.
- **Processors (`processors/`)**: each effect extends `Processor` and implements `process2Swt(...)` for the on-screen preview, `process2Awt(...)` for full-quality rendering, and `openProject`/`saveProject`. Keyframed parameters use the `getNbKeys`/`addKeyGT`/... methods. Every `Clip` starts with a `TimeController` and a `StereoAligner`. `Mixer` subclasses (`AnaMixer`, `SbsMixer`) produce the anaglyph or side-by-side output, and `Renderer` sends frame pairs to the encoder. `Scripter` runs user BeanShell (`bsh`) scripts.
- **Audio**: a video clip carries its own sound, drawn as a bar under its film strip (`VideoTimeLine.SOUND_BAR_H`). The `AudioTimeLine`s hold sound-only clips (`AudioMedia`); like the video lines, they are drawn from the last added (top) down to A1 (bottom), below the video lines, and a clip moved "up" goes to the next index. Each line has `isActive` (checkbox: images and sound) and, for video lines, `soundMuted` (sound icon left of the checkbox); both are saved in the project and used by play and rendering. `Clip.soundOn` mutes one clip (off for the copies made by "duplicate to above line"). Projects of 1.0.7 had the sound as an audio *twin* clip: `TimeLineStack.mergeSoundTwins()` folds it back into the video clip on load.
  - `ffmpeg.AudioReader` decodes a file's first audio stream once into a raw PCM cache (s16le stereo 48 kHz) in `TDenlive.getWorkCacheDir()` = `WorkCache/` sub folder of the project folder, shared by the projects of that folder (`~/3Denlive/WorkCache` before the first save; caches are copied on save; the files of an old `<project>_3De_AudioCache` are moved into it), read by random access, plus a peak envelope for the waveforms. `Media.getAudioReader()` gives it (`StereoMovie`, `AudioMedia`; `null` for still images).
  - `audio.AudioMixer` mixes all the lines (`VideoTimeLine.mixAudio` → `Clip.mixAudio`: processors' `processAudio(...)`, then fades). `audio.AudioPlayer` plays it with `javax.sound` and is the clock of the play loops when there is sound; `RendererGUI` mixes a temporary WAV that `FfmpegEncoder` muxes (AAC in mp4, none for image sequences).
  - Sound processors (`Volume`) return `true` from `Processor.isAudio()` and are listed in `ProcessorLibGUI.AUDIO_PROCESSORS`: allowed on any clip with a sound; image processors are refused on audio-line clips.
  - ffmpeg BMP pipes are read with `Ffmpeg.readBmp()` (cut by the header size): `ImageIO.read` alone misreads concatenated BMPs whose row width is not a multiple of 4.
- **Processing modes**: `TDConfig.PROCESSING_MODE_{WORK,FULLSCREEN,RENDER,AUTOALIGN}`. Each mode has its own resolution/HDR settings, which is why processors receive a mode argument.
- **Adding a processor** means adding it by name string in several places that are not tied together by any registry:
  1. the class in `processors/`;
  2. the GUI in `GUI/processors/` (extends `ProcessorGUI`);
  3. `Clip.openProjectProcessors` (XML tag → instance);
  4. `Clip.addProcessor` (name → instance);
  5. `GUI/ProcessorsGUI` (class name → GUI);
  6. `GUI/ProcessorLibGUI` (library tree entry);
  7. a label in both `res/lngs/EN.xml` and `res/lngs/FR.xml`.
- **GUI (`GUI/`)**: SWT. `TDeGUI` builds the main window (media list, monitor, timelines, properties and processors panels) and runs the event loop. Calls from worker threads must go through `gui.display.syncExec`/`asyncExec`. Imaging is split between SWT (`*Swt` classes, preview) and AWT `BufferedImage` (`*Awt` classes, rendering). macOS constraints: AWT runs headless (set first thing in `main`), because initializing it from a worker thread otherwise deadlocks with the SWT main thread; and drawing on a control outside a Paint event (`new GC(control)`) is ignored, so store the image and call `redraw()` instead; and a shell without `SWT.TITLE` never becomes the key window, so it gets no keyboard events (hence the titled shell of `FullScreenGUI`, whose title bar is hidden in full screen).
- **Scrolling panels**: `CanvasPanel` draws its content from `origin` (scroll bars only move `origin` and redraw). With `CanvasPanel(tde, parent, true)` the horizontal bar is a `Slider` in `bottomRow`, so tools can sit on its right: `TimeLineStackGUI` puts the time zoom there (`setZoom()`: `TimeLineStack.pixPerMS` = `DEFAULT_PIX_PER_MS` × 2^(zoom/10), keeping the time cursor in place).
- **i18n**: all UI strings go through `gui.lngs.get("Section.Key")` and are backed by `res/lngs/EN.xml` and `FR.xml`. Add every new key to both files.
- **Video I/O (`ffmpeg/`)**: decoding and encoding run an external ffmpeg process. The work preview reads a low resolution copy of each video (`VideoReader`, `FfmpegTranscoder.createWorkCopy`), `StringUtils.path2workingcopy()` = `<WorkCache>/<video>_<key>_3De_WorkCopy.mp4` (an old one next to the video is still used); "Save as" copies them to the new work folder. `Ffmpeg.findFfmpeg()` looks for ffmpeg in this order, and the result is cached:
  1. `/usr/bin/ffmpeg`;
  2. `ffmpeg/ffmpeg-<os.arch><suffix>`, relative to the working directory;
  3. `ffmpeg` on the `PATH`;
  4. `/opt/homebrew/bin` and `/usr/local/bin`.
- **Runtime assets** in `distrib/` (`lumas/` transition masks, `frames/` overlay PNGs) are loaded by relative path. The app must therefore run with `distrib/` as its working directory (the launch scripts `cd` into it).

## Conventions

- Hungarian-ish naming: `a` prefix for parameters and locals (`aPath`, `aOs`), class names without prefix. Tabs for indentation.
- Fixed widget heights (`GridData.heightHint`) are written as `tde.gui.h(n)`, where `n` is the height designed for a 12 px text line. `h()` adds the extra height of the real font (`TDeGUI.textH`, measured at startup; the SWT font size follows the system font). Don't use it for the slider canvases (`ScaleBar`, `KeyFrame`) and their rows (`LabelScale`, `LabelKeyFrame`), which contain no text.
- Errors are generally caught as `Throwable` and printed with `printStackTrace(System.err)`, not propagated.
