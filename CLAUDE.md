# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

3Denlive is a stereoscopic (3D) photo/video montage desktop app: plain Java + SWT GUI. There is no Maven/Gradle; everything is built with `javac`/`jar` and shell scripts. The IDE is VS Code, configured in `.vscode/`:
- `settings.json` defines the project as an unmanaged folder: `src` → `bin`, plus `distrib/*.jar` and the Linux SWT for compiling.
- `launch.json` has one run configuration per platform, with that platform's SWT and `cwd` set to `distrib/`.
- `tasks.json` runs the scripts.

Don't reintroduce Eclipse `.project`/`.classpath` files. There are no tests and no linter.

## Build & run

The main class is `com.cubaix.TDenlive.TDenlive`. The code is compiled with `--release 27`, so JDK/JRE 27+ is required.

Each configuration has a folder `distrib/<config>/` with its SWT jar, the natives extracted into `lib/`, and a launcher. The configurations are `Linux`, `PPC64le`, `Win-x64`, `MacIntel` (x86_64) and `MacSilicon` (arm64).
- All folders use SWT 3.135.0 (natives `*-4974r10`) from Maven Central `org.eclipse.platform:org.eclipse.swt.<ws>.<os>.<arch>`.
- An x86_64 SWT fails to load on an arm64 JVM with `UnsatisfiedLinkError: incompatible architecture`.

Dev build into `bin/` (gitignored). Any platform's SWT jar works for compiling:

```sh
javac --release 27 -encoding UTF-8 -d bin -cp "distrib/*:distrib/Linux/swt.jar" $(find src -name '*.java')
```

Dev run: start from `distrib/`, with `src/` on the classpath. The language XML files, images and fonts are loaded with `getResourceAsStream` from `src/`, and `javac` doesn't copy them into `bin/`. `ffmpeg/`, `lumas/` and `frames/` are loaded relative to the working directory.

`./run_3De.sh [-n] [config] [-- app args]` does both steps: it recompiles `bin/` from scratch and runs the app with the config detected from `uname`. `-n` skips the compilation. It runs on macOS and Linux only. The app's standard and error outputs go to `log/3De.log` (gitignored, replaced at each run). The app accepts a project file as its only argument (`./run_3De.sh -- my.3De`). By hand:

```sh
cd distrib && java -XstartOnFirstThread -Xmx4G -XX:G1PeriodicGCInterval=30000 --enable-native-access=ALL-UNNAMED -cp "../bin:../src:*:MacSilicon/swt.jar" -Djava.library.path=MacSilicon/lib com.cubaix.TDenlive.TDenlive
```

On Linux, drop `-XstartOnFirstThread`, use the `Linux/` jar and libs, and set `GTK_OVERLAY_SCROLLING=0`. The README has the per-platform variants. Started from a snap application (VS Code installed as a snap), the environment carries the snap's `GIO_MODULE_DIR`, `GTK_PATH`, `LOCPATH`... whose modules, built against the snap's libc, make the `WebKitNetworkProcess` crash (`undefined symbol: __libc_pthread_init`: no web page loads, "offline" message): the Linux launchers and `run_3De.sh` unset those that point into a snap (`SNAP` itself is not always passed on), drop the snap folders of `XDG_DATA_DIRS` and restore the `*_VSCODE_SNAP_ORIG` variables; `utils.SnapEnv.clean()`, first in `main()` on Linux, does the same in the native environment of the process (libc `unsetenv` / `setenv` through the FFM API, before GTK starts), for the VS Code launch configuration.

`./Install-Dev.sh` downloads two kinds of binaries into gitignored folders:
- ffmpeg into `distrib/ffmpeg/`. The binaries are not in Git or in the jar because they are 60 to 180 MB each. The files are named `ffmpeg-<os.arch><suffix>`: `ffmpeg-amd64`, `ffmpeg-amd64.exe`, `ffmpeg-x86_64-osx`, `ffmpeg-aarch64-osx`. `SOURCES.txt` records where each one came from.
- A Java 27 JRE per config into `JVMs/<config>/`: Temurin, or Azul Zulu for MacIntel because Temurin has no macOS x64 build.
- A Java 27 JDK for the host machine into `JVMs/JDK/`.
- JavaFX for the Linux config into `distrib/Linux/javafx/` (see Demos below).

Its options are config arguments, `--ffmpeg-only`, `--jvm-only`, `--jdk-only` or `--javafx-only`, and `-f` to re-download the latest releases.

`run_3De.sh` and `build_delivery.sh` don't trust the default `javac` / `java` (a Linux machine may have javac 8 and java 25): `find_jdk.sh` (sourced) looks for a Java 27+ tool in `JAVA_HOME`, on the `PATH`, in `JVMs/JDK/`, then among the installed JDKs (`/usr/lib/jvm`, `/Library/Java/JavaVirtualMachines`...). `run_3De.sh` compiles with that JDK but runs with the JRE of the delivery of the host config, `JVMs/<config>/bin/java`, and only falls back to `find_jdk.sh` when it is missing.

`./build_delivery.sh [config...]` builds the deliveries:
- It compiles into `delivery/build/`, copying the resources next to the classes, then builds the jar.
- Each config gets a self-contained `delivery/3Denlive<config>.tar.gz`, except Windows, which gets a `.zip`. The archive contains the jars, SWT, `lumas/`, `frames/`, the platform's `ffmpeg/`, `jre/`, `javafx/` for Linux and the launcher.
- The launchers (`distrib/<config>/3Denlive.sh`, `Win-x64/3Denlive.bat`) use `./jre` when it is present, and the system java otherwise.
- PPC64le has no bundled ffmpeg and uses the system one.

`distrib/3Denlive.jar` is tracked in Git but not regenerated by any script.

## Version

The version lives in `src/com/cubaix/TDenlive/VERSION.txt` (one line, `X.Y.Z`). `TDenlive.TDeVersion` reads it with `getResourceAsStream`, and `build_delivery.sh` reads it for its output. **After any code change, increment the last number (Z) by 1**, once per set of changes, not once per file.

## Architecture

All code lives in `com.cubaix.TDenlive`, with a vendored Nebula `TableCombo` widget under `org.eclipse.nebula`.

- **`TDenlive`** is the app root. A single instance is passed to almost every constructor as `tde`/`aTDe`, and it holds `config` (`TDConfig`), `gui` (`TDeGUI`), `mediaList`, `timeLineStack` and `selected`. It also writes and reads the project file.
- **Persistence**: projects (`<3De>…</3De>`) and the user config (`~/3Denlive/3De.conf`) are hand-built XML. They are written by appending to a `StringBuffer` in each class's `saveProject(StringBuffer)`. They are read with the custom `xml.XmlMinimalParser`, which turns the file into a flat `Vector<XmlObject>`. Each class's `openProject(Vector<XmlObject> aOs, int o)` consumes tags from index `o` and returns the new index; a tag's text is in `aOs.elementAt(++o).text`. Follow this cursor pattern for any new persisted field, and keep save and load symmetric. The parser lowers the tag names: a value tag must not have the name of its enclosing tag in another case (`Speed` reads its `<speed>` values by skipping its opening tag and consuming each `</speed>`).
- **Project folder**: "Save" opens `GUI/SaveProjectGUI` (name, folder typed or chosen with a `DirectoryDialog`, "create a new folder for the project" checkbox, checked for a never saved project: `<folder>/<name>/<name>.3De`), not a native save panel. When the project folder changes (and not when saving before quitting), `TDeGUI.offerGather()` proposes to move, copy or leave the media files outside it: `utils.ProjectFiles.relocate()` puts them at the root of the project folder (`name_2.ext` if taken), with their computed depth maps, WorkCache work copy and sound cache renamed for the new path (`AudioReader.cacheFileFor()`; a move that fails becomes a copy), rewrites the paths in the project XML, saves it and opens the project again. Adding a file from outside the folder of a saved project (`OpenMediaGUI.askCopy()`) proposes to copy it there (`ProjectFiles.importFile()`, in the loading thread; a copy with the same name, size and date is reused).
- **Media model (`medias/`)**: `Media` (abstract, extends `GUI.Drawable`) has these subclasses:
  - `StereoImage`, with `StereoMovie`, `StereoSvg` and `ColorBck` extending it. `utils.MpoReader` handles MPO stereo photos.
  - `ColorBck` (palette button of the media list toolbar, `GUI/ColorBckGUI`) fills the output frame with `ColorBck.Fill`: a plain color, a procedural texture of two colors (category `geometric`: `Fill.TEXTURES`, plain first then the 2x2 checkerboard of the monitor, light gray / white like `ImageUtils.checkerBck()`; `Fill.mix(u, v)` per tile, 2 x 2 samples per pixel) or a bitmap (`bmp:<category>/<id>` = `res/textures/<category>/<id>.jpg`, color maps of ambientCG materials, CC0, 1K recompressed, see `res/textures/LICENSE.txt`, except the `brushed/Brushed*` and `Circular*` metals generated procedurally (periodic anisotropic value noise, seamless; circular: for one repeat); categories and order in `res/textures/textures.txt`, names `ColorBck.Cat_<category>` / `ColorBck.Tex_<id>`; the image scaled to the tile (halvings then bilinear) and repeated; the colors disabled; the W / H link keeps its proportions; category combo + thumbnails = `GUI/TextureLibrary`, shared with the 3D modeler) or an image of the disk ("Load an image..." button: `file:<path>`, category `files` = `Fill.files`, the images of the session; saved as `<texture>file</texture>` + `<texturePath>`, alone in its tag and returned by `getFilePaths()` so that the gathering, the packing and the renaming of the medias handle it; read back with `findPath()`), tiles of `tileW` x `tileH` % of the image height (0.5 to 400 %, logarithmic sliders), start `tileX` / `tileY` % of the tile, rotation `tileRot` (degrees counterclockwise around the top left corner of the image, -180..180 slider + "0°"; a turned bitmap is sampled bilinearly in its scaled tile, else the fast integer tiling); saved only when not plain (`<texture>`, `<color2>`, `<tileW>`...). The form: checkboxes linking W / H and X / Y (the other slider takes the same value), preview at 100 % (`Fill.paint(image, refH)`: top left corner of the image at the RENDER height).
  - `Clip`, a placement of a media on a timeline. It owns an ordered `processors` list and links to its twin clips.
  - `VideoTimeLine` and `AudioTimeLine`.
  - `TimeLineStack`, which composes the timelines.
  - `ShapesMedia` (shapes clip, created from the media list toolbar with the `GUI/ShapesClipGUI` popup) holds the initial vector shapes (`shapes.Shape`, frame coordinates 0..1, a depth = L/R parallax). Its clips get the mandatory `processors.Shapes` (undeletable, unmovable, right after the `TimeController`): every key holds all the shapes (same ids and order), interpolated between keys; a deleted shape is only `hidden` from its key on. `shapes.ShapesEditor` is the shared vector editor (popup canvas, shown in the monitor's view mode: `Mixer.copyMode()` + `Mixer.mix2Swt()` on the left/right renders, same per-eye views; and `MonitorGUI` overlay when the selected clip has `Shapes`: an edit at a time without a key adds one there); `GUI/ShapesPanel` holds its tools and properties. On the monitor, the editor views (`ShapesEditor.View`) map the shapes through the geometry of the active processors after `Shapes` (`Shapes.getChainTransform()` composes `Processor.getGeometry()`: affine, per eye; only `StereoAligner`, via its shared `computeGeometry()`, and `Placer` move the image, the others count as identity). When the mixer shows both eyes on one image (anaglyph...), each frame has a left and a right view (same `group`): a click picks the nearest handle or shape image of either eye, the handles of a shape shifted in depth are drawn for both eyes (red / cyan), once when they coincide.
  - Subtitles: `processors.Subtitles` ("Video" folder of the library) extends `Shapes` with a single text shape (keys like `Shapes`; before interpolating, `interpolate()` gives every key the text of the time, so that the line height is interpolated), drawn over any clip in the frame of the montage (output at the montage size, image at its top left corner). Its cues come from a `.srt` / `.vtt` file read by `utils.SubtitleFile` (file dialog opened when the processor is added, "Add a subtitle" button of `GUI/processors/SubtitlesGUI`) and are saved in the project (`<cue>start;end;text</cue>`). The text at a time is the cue of the media time (`time - startTimeMS + shiftTimeMS`; the last started among overlapping cues), set with `Shape.setTextKeepLines()`: same line height, the middle of the bottom side stays, so texts of several lines grow upward. `ShapesPanel` in single text mode (no tools) edits its style; its text field changes the current cue.
  - Speed: `processors.Speed` ("Video" and "Sound" folders of the library, same entry, `GUI/processors/SpeedGUI`, logarithmic slider + % field, 10 to 800 %) on any clip of a video or a sound (audio lines too), one per clip. Keyed speed, a function of the media time (its keys are in media time like the others), linear between the keys: `Speed.timeSpan()` (time line duration to play a media span, integral of 1/speed, log on each piece) and `Speed.advance()` (its exact inverse, exp) give `Clip.mediaTimeD()` / `mediaTimeMS()` (kept inside the media), used by `reBuild` (paired depth clips included), the film strip, the waveform, the sound, `Subtitles` and `Objects3D`, and `timeForMediaMS()`. `cutAt` / `trimStart` / `trimEnd` use them. Any speed change (slider, field, key deletion, (de)activation, removal) goes through `Clip.keepMediaEnd()`: the media time at the end of the clip is kept, so the clip duration on the time line follows (slower = longer), and the time cursor, if in the clip, stays on the same image. `Clip.TimeRef` (media times of the clip end and of the cursor, `timeRef()`) is the reference of the change; a drag of the speed slider takes it once at its start (`LabelScale.isDragging()`, `changeEnd()` at the mouse up, from `ScaleBar`) and edits the same key all along (by its key time, unchanged by the speed), so that the roundings to the ms of the time line don't accumulate; the next drag starts from the effective times. `Speed` is unmovable, right after the `TimeController` (`Shapes` / `Objects3D`) and the depth processor (`Clip.placeSpeedProcessor()`, also at the loading); its keys and those of all the other processors are in media time (whatever their position), so they stay on the same images whatever the speed: every conversion goes through `Processor.keyTime(timePos)` / `keyTimePos(keyTime)` (→ `Clip.keyTimeAt()` / `keyTimePos()`; without speed, the same as `timePos - getKeysOriginMS()`) and `Processor.isKeyAt()` (equal key time, or equal time line position: with a speed, the round trip is not exact). A clip cut with a speed gets `keysMediaShiftMS` (saved only when not 0) so that its media keys keep their origin. The sound is resampled (`Clip.readAtSpeed()`: pitch follows the speed), or, with the "Keep the pitch of the sound" option (`Speed.keepPitch`, `<keepPitch>`), time stretched by `audio.TimeStretch` (WSOLA: grains of 40 ms every 20 ms, Hann windows, each read at its position on the speed curve and shifted by at most ±10 ms to best continue the previous grain; a grain only depends on its index and the cached shift of the previous one, so any buffer can be computed alone; `Clip.stretch`, reset at each speed change).
  - Text fonts go with the project: `shapes.ProjectFonts` copies, at the save, the files of the families named by the `<fontName>` tags of the project XML (all their styles, found among the fonts already registered from a project, else in the system font folders) into `Fonts/<project>/` next to the `.3De`, removes the unused ones, registers them at the opening, and `packProject` zips them. Roboto (embedded) and the Java logical fonts are not copied. The texts (`ShapeText` layouts, `Mesh3D.text()`) take their font from `ShapeText.font()`: the faces loaded from files (embedded Roboto, fonts of the project: `ShapeText.OWN`, `addOwn()`; face chosen by its name for bold / italic, regular weight preferred) before a system font of the same name, because `registerFont()` does nothing when one is installed (another Roboto on Linux: other line metrics, texts of another size).
  - The thumbnails of the media list carry badges at their bottom left (`MediaList.drawBadges()`, drawn with the GC, translucent black): the kind (`kindOf()`: image, video = `StereoMovie`, sound = `AudioMedia`, shapes and 3D model with the icons of their toolbar buttons `colorObjects.png` / `cube3d.png`), then for images and videos "2D" or "3D" with anaglyph fringes (`isStereo()`: `origStereo` != 0 or two different files; shapes and 3D models 3D, color backgrounds 2D).
  - Each media row of the media list has a trash button (drawn by `MediaList.drawSwt()`, hit by `trashAt()`; `MediaListGUI.trashMedia()`): if the media is used by clips of the time lines (`TimeLineStack.clipsOf()`) or as the depth map of a `DepthmapStereo` key (`depthUsesOf()`), a confirmation first; then `TimeLineStack.releaseMedia()` removes its clips (with their twins) and those depth references, and `MediaList.removeMedia()` removes it.
  - Timeline clips draw a film strip: `Media.getThumbAwtAt(time)`. For `StereoMovie` it comes from `ffmpeg.VideoThumbnailer` (one background ffmpeg run per video, one video at a time); the single `buildThumb()` image is only the media list thumbnail and is no longer rebuilt at each frame.
- **Processors (`processors/`)**: each effect extends `Processor` and implements `process2Swt(...)` for the on-screen preview, `process2Awt(...)` for full-quality rendering, and `openProject`/`saveProject`. Keyframed parameters use the `getNbKeys`/`addKeyGT`/... methods. Key times are relative to `Clip.getKeysOriginMS()` = `startTimeMS - keysShiftMS`, not to the clip start: the second part of a clip cut with the scissors (`Clip.cutAt`, "Cut at position" button right of "Delete clip" in the clip panel, `TimeControllerGUI`) keeps the same keys with `keysShiftMS` = the cut offset, so keys may lie before the start or after the end of a clip. In the GUIs, a parameter setter takes its key from `LabelKeyFrame.editKey()`: the key exactly at the time cursor, else a new interpolated key inserted there (the widgets are refreshed from it afterwards with `asyncExec`). This is the automatic mode. Above the K row of each processor (`LabelKeyFrame`), a "Select" button adds to the selection the key at the time cursor, else the nearest one on its left (`Processor.selectKeyGT()`; `selectedKeyTimes`, by key time, the last selected being the main one), drawn as yellow squares by `KeyFrame`; "Unselect" clears it and goes back to the automatic mode (`isAutoKey()` = no selected key). The selection is saved by `Clip` as `<ProcSelKeys>t1;t2</ProcSelKeys>` after the processor (the old `<ProcAutoKey>` is ignored). In automatic mode the widgets show the values interpolated at the cursor (`LabelKeyFrame.displayKey()` → `Processor.setDisplayKeyGT()` + index `Processor.DISPLAY_KEY`, read by the getters through each processor's `key()`; the real keys are untouched); with a selection they show the main selected key. A change while the montage plays pauses it first (`PlayerControlGUI.pauseForEdit()`, from `LabelKeyFrame.edit()` / `editKey()`, the add / delete key button and `Shapes.ensureCurrentKey()`): one key at the time of the change, not one per image played. The GUIs change a parameter with `lkf.edit(aEK -> proc.setX(aEK, v))`: the same value goes to all the selected keys, else to `editKey()`. `Shapes.manualKey()` (main selected key) is what the shapes editor edits then, and `Shapes.syncSelectedKeys()` (editor listener) copies each shape changed in it into the other selected keys; its clicks hit the shapes where they are drawn (`ShapesEditor.Source.getDisplayedShapes()`, interpolated; the edited key shape of the same id is moved), plus the outline of the selected shape at its key place; only the selected shape has handles. Every `Clip` starts with a `TimeController` and a `StereoAligner`. Focus: each processor title (not the `TimeController`) has an icon `focusOn.png` / `focusOff.png` (viewfinder, crossed out in gray when off; `ProcessorsGUI.focusIcons`, `showFocus()`, tips `Tip.ProcFocusOn` / `Tip.ProcFocusOff`): `Clip.focused` (session only, `getFocused()` / `setFocused()`) is the processor the changes are for; a click on the icon gives / removes it; any click, selection or key in the panel of a processor (not in its title: `PROC_TITLE`; box `PROC_BOX`, display filters of `ProcessorsGUI`) gives it the focus and removes it from the others, as an edit of the shapes on the monitor does, and adding a processor (`Clip.addProcessor()`). The shapes / subtitles edited on the monitor are `Clip.getEditedShapes()`: the last `Shapes` (or `Subtitles`) focused, else the first (`MonitorGUI.getEditedShapes()`, `History.shapesOf()`), so that several subtitles of a clip can each be edited. The processors are in a `ScrolledComposite` whose minimum height follows its content (`ProcessorsGUI.updateScroll()`: at its resize, after a title click, at the end of `setProcessors()`, and when a box changes its size, `scrollLater()`), so that the last processors can be reached once panels are expanded. Expanded / collapsed processors in the panel: `ProcessorsGUI.EXPANDED` (by processor class, session only, a class never toggled = collapsed) is applied when the processors of another clip are shown (`shownClip`; shown again for the same clip: their own `isExpended` kept, so a processor just added stays open); each title click and "collapse all" records it. `Mixer` subclasses (`AnaMixer`, `SbsMixer`) produce the anaglyph or side-by-side output, and `Renderer` sends frame pairs to the encoder. `Scripter` runs user BeanShell (`bsh`) scripts.
- **Depth maps (`depth/`)**: `Depthmap` (2D + depth map) and `DepthmapStereo` can compute their depth maps with Depth Anything V2.
  - **When**: when one of them is added from the library (`ProcessorLibGUI`) to a clip, `GUI/DepthmapConvertGUI` behaves as follows:
    - it uses the existing `_3eDepthMap` files of the media without asking;
    - otherwise, when the clip has no depth map, it proposes the computation (`DepthConverter.hasDepthmap()`: not a single 2D file, and a gray right view with a non-gray left view);
    - the button of the processors' GUIs computes them again (`aForce`).
  - **Placement**: a clip has at most one depth processor (`Clip.getDepthProcessor()`; adding a second one is refused). It is always first after the `TimeController` (and `Shapes` / `Objects3D`, `Clip.isHeadProcessor()`), before `Speed` (the inpainting signatures, made of the processors before it, then do not depend on the speed), unmovable: see `Clip.placeDepthProcessor()`, also applied at the loading.
  - **Models**: the user chooses the model in `DepthModel`: Small is Apache-2.0, Large is CC-BY-NC-4.0.
  - **GPU or CPU**: both models run on the GPU when one has at least `DepthModel.gpuMemory` free (1.5 / 5 GB, from the peak footprints measured with WebGPU).
    - Only two GPU providers exist in the Java builds of ONNX Runtime 1.31: WebGPU/Metal, in the standard jar for macOS only, and CUDA, in the `onnxruntime_gpu` jar (Windows x64 / Linux x64, 385 MB, needs CUDA 12 + cuDNN 9 installed). `DepthEstimator.useGpuRuntime()` downloads the CUDA jar instead of the standard one when `nvidia-smi` is found. The other Windows / Linux machines, and the integrated Intel / AMD GPUs, compute on the CPU.
    - `DepthEstimator.bestGpu()` takes the NVIDIA GPU with the most free memory (`nvidia-smi` index, passed to `addCUDA`; it matches the CUDA order with `CUDA_DEVICE_ORDER=PCI_BUS_ID` or identical cards). When all of them are full, the CPU is used. On macOS (unified memory), the free memory comes from the free + reclaimable pages of `vm_stat`, capped at 3/4 of the RAM.
    - The GPU providers are tried in this order: CUDA, then WebGPU. If CUDA fails (`CPU_REASON_CUDA`, usually CUDA / cuDNN missing) or the GPU fails during the run, the estimator goes on with the CPU (`cpuReason`).
    - The progress window says whether the computation runs on the GPU or the CPU and why, but never the provider name ("WebGPU" suggests that data leaves the computer).
    - CoreML is not used: on Apple Silicon it is 3 to 15× slower than the CPU on these models, whereas WebGPU is about 5× faster.
  - **Child process**: the public `DepthEstimator` constructor starts a child JVM (`DepthEstimator.main()`, same java and classpath, `-Xmx2G`, binary protocol on stdin / stdout, logs on stderr) that loads the model with the package constructor `DepthEstimator(dir, model, true)`; `estimate()` sends the image resized to the model size and reads the depth back; `close()` stops the child. Reason: ONNX Runtime keeps its native memory (about 2 GB for Large, CPU or WebGPU) after its session is closed, until the end of the process. The Python generators are child processes too, killed by a shutdown hook if the application quits. The launchers add `-XX:G1PeriodicGCInterval=30000` so that the Java heap given back after a big job (video decoding...) is returned to the system when idle.
  - **Downloads**: at the first use, the ONNX models (Hugging Face `onnx-community/depth-anything-v2-*`) and the ONNX Runtime jar (Maven Central, standard or CUDA build) are downloaded into `~/3Denlive/Models/`. The jar is not in `distrib/`, the classpath or the deliveries: `DepthEstimator` loads it with its own `URLClassLoader` and calls it by reflection. Its natives exist only for Windows x64, Linux x64/arm64 and macOS arm64 (`isPlatformSupported()`).
  - **Files**: `DepthConverter` writes one file per source file, next to it: `<name>_3eDepthMap.png`, or `.mp4` without sound (`ComputedDepthmap.depthPath()`). It falls back to the WorkCache when the folder is read-only.
    - The file keeps the stereo layout of the source: a side-by-side source gives a side-by-side map, and an MPO gives a parallel PNG.
    - All the views are computed, whatever the processor. White is front, so `blackIsFront` is set to false.
    - For video, it decodes with `FfmpegDecoder`, smooths the depth levels across frames, and encodes gray frames with `ffmpeg.FfmpegRawEncoder`. The steps without a counter of the progress window (`DepthConvert.Finishing`: end of that encoding; `DepthConvert.Loading`: opening of the result) show their elapsed time every second (`DepthmapConvertGUI.tickPhase()`); the work copy of the depth video is made afterwards in the background, with its progress on the monitor.
    - After a new computation, `ComputedDepthmap.forget()` drops the loaded medias and the video work copy.
  - **Attachment**: the maps are not added to the media list. `depth.ComputedDepthmap` (the processor's `computed` field) finds the files back from the clip's media (`find()`).
    - It loads them into a media cached by file name, in the source's layout. A video gets its work copy in the WorkCache like any other, and `StereoMovie.noSound`.
    - It gives the clip a paired clip with `followsOrientation`, which copies the rotation and anamorphosis of the clip's media in `Clip.reBuild`.
    - Processors only save `<computedDepth>true</computedDepth>`.
    - `TDenlive.packProject` adds the files next to the packed medias, named after the packed name. "Save as" copies those in the WorkCache.
    - `Processor.removed()` (called by `Clip.removeProcessor`) releases the paired clip.
  - **Depth map used**: `Depthmap` uses the left computed map if any, else the right view of the media (2D + depth map). `DepthmapStereo` uses the key's own depth media if any, else the computed maps (shown as "(computed)" in its combo), one per view. The maps are resized to the views with `ImageUtils.fitTo`.
  - **Mix (M)**: a keyed parameter `m` (0..1, slider M 0..100, `<m>` tag) of both processors mixes the depth map on the source before the conversion (`Depthmap.mixDepth()`: colors only, the source alpha is kept): 0 = the source as before, 1 = the depth map converted to stereo instead of the image.
  - **Display**: the "Show the depth map" checkbox, right of the compute button, sets `showDepth` (not saved). Outside the RENDER mode, the processor then outputs the depth maps instead of its result.

A clip dragged on the time lines follows the line under the mouse, of the same kind (`TimeLineStack.moveClipToLine()`). Files dragged from the file manager onto the media list (`GUI/MediaDropGUI`, SWT `FileTransfer`, always a copy operation, handled in an `asyncExec` after the drop): the sounds (`OpenMediaGUI.AUDIO_EXTS`) are added as sounds; for the others one type is asked for all of them (2D, parallel, crossed, left + right = the files sorted by name taken two by two, enabled with an even count; the last type chosen is the default button), MPO and `.ply` keep their own reading; folders, `.3De` and work copies are ignored (warning); then the copy into the project folder is proposed (`askCopy()`, as `OpenMediaGUI`) and the files are loaded in a thread.
- **Scrolling panels**: `CanvasPanel` draws its content from `origin` (scroll bars only move `origin` and redraw). With `CanvasPanel(tde, parent, true)` the horizontal bar is a `Slider` in `bottomRow`, so tools can sit on its right: `TimeLineStackGUI` puts the time zoom there (`setZoom()`: `TimeLineStack.pixPerMS` = `DEFAULT_PIX_PER_MS` × 2^(zoom/10), keeping the time cursor in place).
- **i18n**: all UI strings go through `gui.lngs.get("Section.Key")` and are backed by `res/lngs/<LNG>.xml`: EN, FR, DE, ES, IT, PT, same lines and labels in all (a missing key falls back to EN). Add every new key to all of them. The languages are listed in `Lngs.LANGUAGES`; at the first start (no `3De.conf`), `GUI/LngChooser` shows one flag button per language (`res/imgs/<LNG>.png`, 64x40), 3 per row. The pages of the web site are taken in the interface language when the server has them, else in English (`WebBrowserGUI.localized()`: `pageExists()` = HEAD below 400, the missing pages answer 500; cached, 2 s connection timeout): the news page shown at startup `newsXX.php` (`newsURL()`), the demos page (`demosURL()`) and the user guide `doc/XX/` (`guideURL()`, system browser). The AI prompt examples are translated in FR only (`ai_prompts_FR.txt`), English otherwise. The language selector of `SettingsGUI` calls `TDeGUI.setLanguage()`, which rebuilds the main window contents (`rebuildContents()`: the views are kept) and translates the processor names already created (`Lngs.translate()`); open secondary windows other than the settings keep the old language until reopened. Strings read once into long-lived objects need the same treatment.
- **Video I/O (`ffmpeg/`)**: decoding and encoding run an external ffmpeg process. The video files are recognized by extension (`MediaList.VIDEO_FILE_RE`: mp4, m4v, mov, mkv, webm (VP8 / VP9 / AV1, Opus / Vorbis: read by ffmpeg like the others), avi, mpg, ts, mts, m2ts, dv...; the filters of `OpenMediaGUI.fileChoose()` and `AiClipGUI.VIDEO_EXTS` list the same); another extension is loaded as an image. The work preview (all the modes but RENDER) reads a copy of each video (`VideoReader`, `FfmpegTranscoder.createWorkCopy`: height `processingResValues[WORK]` of the monitor, never enlarged, 15 fps, H.264 CRF 18 veryfast), `StringUtils.path2workingcopy()` = `<WorkCache>/<video>_<key>_3De_WorkCopyHQ.mp4` (the `_3De_WorkCopy.mp4` of 1.11.6 and before, 576 lines at 300 kbit/s, are no longer used; `oldWorkingCopy()` deleted when a new one is made). Seeks on the frame grid (`FfmpegDecoder(..., aFileFps)`: position moved to the nearest frame k of the file read, work copy `min(15, origFps)` or original, `-ss` half a frame before it, first frame labeled `firstMS` = k / fps; before, the first frame at or after the position was labeled with the position: up to a frame late, a different lag per video, a mask video off its original). `VideoReader.checkWorkCopy()` makes it again when it is missing or its height (first image decoded) is not that of `workSize()`; meanwhile the original is read, reduced to that size (`evalResize()`). Always a copy at 15 fps, whatever the work resolution: at the size of the original when the work resolution is not below it (`useOriginal()`: read without resize). The work resolution is 576 (DVD) by default (`TDConfig.processingResValues[WORK]`). A change of the work resolution (monitor combo, `SettingsGUI`) calls `VideoReader.workResChanged()`: every video opened (`READERS`) is checked again in the background; `MAKING` = the copies in progress (checked again at their end), shown over the top left corner of the monitor (`MonitorGUI.drawWorkCopies()`, `Monitor.WorkCopies`) with their progress and the time left (`FfmpegTranscoder.workCopyProgress()`: the `time=` of the progress lines of ffmpeg, `Ffmpeg.progressMS`, against their durations; `Monitor.WorkCopiesLeft`), redrawn every second meanwhile. "Save as" copies them to the new work folder. `Ffmpeg.findFfmpeg()` looks for ffmpeg in this order, and the result is cached:
  1. `/usr/bin/ffmpeg`;
  2. `ffmpeg/ffmpeg-<os.arch><suffix>`, relative to the working directory;
  3. `ffmpeg` on the `PATH`;
  4. `/opt/homebrew/bin` and `/usr/local/bin`.
- **Rendering window (`GUI/RendererGUI`)**: renders in two passes, as the clip of a time range (`processors.TwoPassRender.run()`), only when a clip rendered (active line, in the range, solo clips) has an active `SceneCamKeys` with the smart filling by SDXL (`fillModel`) and the F/F+1 carry-over (`carriesFilling()`; else the output alone): first the keyframes, `KEY_FPS` 10 images per second from the start (status `Renderer.KeyPass`, `%FPS%` = `keyFpsText()`; shown in the monitor, not encoded), of which only the memory of the filling of the 3D scenes is kept in `<WorkCache>/RenderKeys_<ms>/` (`SmartFill.prevMark()` / `savePrevSince()`: the `Prev` images made for it, colors in 8 bits, gzip; folder deleted at the end); then the output at its rate, every image computed: just before the first image whose time is not before that of a keyframe, `SmartFill.restorePrev()` makes the memory of that keyframe the latest of its streams, so that the F/F+1 carry-over starts from the keyframes (no drift accumulated over the output images). the output path is shown without format suffix; checkboxes choose the formats (`FfmpegEncoder.FORMAT_SUFFIXES`: `_P` (checked by default), `_X`, `_Left`, `_Right`, `_A`, `_Dubois`, inserted before the extension by `withSuffix()`), all made in one pass: one ffmpeg process, the parallel BMP stream split by a `-filter_complex` (`stereo3d=sbsl:sbsr` / `ml` / `mr` / `arcc` / `arcd`, `format=rgb24` before the anaglyphs: stereo3d reads `bgr24` as RGB; single views cropped to even sizes), the options and the sound repeated per output, `frame-packing=3` only for `_P`. The checkbox "Anaglyphs with colors at full resolution" (`anaglyph444`, enabled when an anaglyph is checked, note `Renderer.Anaglyph444Note` on quality and portability) sends `_A` / `_Dubois` to a second ffmpeg process in `yuv444p` (H.264 High 4:4:4: no halved chroma blurring the eyes, but not played by Safari / iOS, most phones and TVs); `Renderer` writes each image as BMP once (`addBmp()`) for both encoders. At each counters refresh (`updateStatus()`), an anaglyph thumbnail of the last produced pair with the progress percentage over its bottom right corner. The monitor shows the images produced meanwhile (`MonitorGUI.setRendering()` at the start / in `stop()`, `showRendered()` after each pair: mixed in the mode of the monitor by `Mixer.mix2Swt()` (FULLSCREEN, HDR images made 8 bits) in a thread of its own at the monitor size, one mix at a time, the latest pair waiting wins: the rendering never waits; drawn by `drawDbl()` instead of the media). The time cursor follows the image just produced (`setRequestedTimePosMS()` in the `asyncExec` of each pair, time lines and monitor ruler redrawn; back to the start in `stop()`); the ruler ignores the clicks meanwhile (`MonitorGUI.isRendering()`). At the end of a video rendering (not an image sequence), `utils.HtmlViewer` writes one page `<video>.html` per video made, next to it (in the order `VIEWER_ORDER`: `_P`, `_X`, `_Dubois`, `_A`, `_Left`, `_Right`; all opened at the end by `RendererGUI.openPages()`, in reverse order with a pause between them so that the most suited tab is in front; `data-layout` `sbs` / `crossed` / `mono` / `anaglyph` = `FORMAT_LAYOUTS`: a crossed file is recomposed in every mode, mono and anaglyph files are shown as they are, without the format selector) and its preview `<video>.preview.jpg` (first image `Renderer.firstP` in the layout of that format, `RendererGUI.previewFor()`), shown by the player without reading the video until it is played (as the player of the web site), opened in the default browser (`BrowserControl.openFile()`) when the end popup (files and pages made) is closed; the instant images ("SaveView", `TDeGUI.saveCurrentImage()`; the camera button left of the full screen one in the monitor toolbar, `TDeGUI.snapshotToLibrary()`, renders the monitor media at the time cursor in RENDER mode and adds both views side by side, 8-bit PNG `Snapshots/<project>_Snapshot_NNNN.png` next to the project, to the media list with `loadImageP`; the video camera button `videoCamera.png` right of it, `GUI/RangeClipGUI`, renders in the same way the time range of the ruler, else the selected clips alone (`TimeLineStack.soloClips` with their twins, respected by `VideoTimeLine` for images and sound; from the earliest start to the latest end), at the default rendering resolution and `outFps`, parallel with sound, into `Clips/<project>_Clip_NNNN.mp4`, added with `loadImageP`; the monitor shows its images as they are made, and the time cursor follows them (`setRendering()` / `showRendered()`, as the rendering window); neither: a warning `Monitor.RangeClipNoRange`) get `<base>.html` the same way (player on the parallel image, then the left, right, crossed and parallel images under centered `Html.*` titles). The pages embed `res/html/stereoplayer.js`, a copy of https://3denlive.com/stereoplayer.js (preview image, loading queue, shared WebGL context) with image support (`data-type="image"`), `data-layout` and a Canvas 2D fallback when WebGL refuses a `file://` source; they reference the media by file name (same folder).
- **Runtime assets** in `distrib/` (`lumas/` transition masks, `frames/` overlay PNGs) are loaded by relative path. The app must therefore run with `distrib/` as its working directory (the launch scripts `cd` into it).

## Conventions

- Hungarian-ish naming: `a` prefix for parameters and locals (`aPath`, `aOs`), class names without prefix. Tabs for indentation.
- Fixed widget heights (`GridData.heightHint`) are written as `tde.gui.h(n)`, where `n` is the height designed for a 12 px text line. `h()` adds the extra height of the real font (`TDeGUI.textH`, measured at startup; the SWT font size follows the system font). Don't use it for the slider canvases (`ScaleBar`, `KeyFrame`) and their rows (`LabelScale`, `LabelKeyFrame`), which contain no text.
- Errors are generally caught as `Throwable` and printed with `printStackTrace(System.err)`, not propagated.
