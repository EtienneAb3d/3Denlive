# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

3Denlive is a stereoscopic (3D) photo/video montage desktop app: plain Java + SWT GUI. There is no Maven/Gradle; everything is built with `javac`/`jar` and shell scripts. The IDE is VS Code, configured in `.vscode/`:
- `settings.json` defines the project as an unmanaged folder: `src` → `bin`, plus `distrib/*.jar` and the Linux SWT for compiling.
- `launch.json` has one run configuration per platform, with that platform's SWT and `cwd` set to `distrib/`.
- `tasks.json` runs the scripts.

Don't reintroduce Eclipse `.project`/`.classpath` files. There are no tests and no linter.

## Build & run

The main class is `com.cubaix.TDenlive.TDenlive`. The code is compiled with `--release 27`, so JDK/JRE 27+ is required.

Each configuration has a folder `distrib/<config>/` with its SWT jar, the natives extracted into `lib/`, and a launcher. The configurations are `Linux`, `PPC64le`, `Win-x64`, `MacIntel` (x86_64) and `MacSilicon` (arm64).
- All folders use SWT 3.135.0 (natives `*-4974r10`) from Maven Central `org.eclipse.platform:org.eclipse.swt.<ws>.<os>.<arch>`.
- An x86_64 SWT fails to load on an arm64 JVM with `UnsatisfiedLinkError: incompatible architecture`.

Dev build into `bin/` (gitignored). Any platform's SWT jar works for compiling:

```sh
javac --release 27 -encoding UTF-8 -d bin -cp "distrib/*:distrib/Linux/swt.jar" $(find src -name '*.java')
```

Dev run: start from `distrib/`, with `src/` on the classpath. The language XML files, images and fonts are loaded with `getResourceAsStream` from `src/`, and `javac` doesn't copy them into `bin/`. `ffmpeg/`, `lumas/` and `frames/` are loaded relative to the working directory.

`./run_3De.sh [-n] [config] [-- app args]` does both steps: it recompiles `bin/` from scratch and runs the app with the config detected from `uname`. `-n` skips the compilation. It runs on macOS and Linux only. The app's standard and error outputs go to `log/3De.log` (gitignored, replaced at each run). The app accepts a project file as its only argument (`./run_3De.sh -- my.3De`). By hand:

```sh
cd distrib && java -XstartOnFirstThread -Xmx4G -XX:G1PeriodicGCInterval=30000 --enable-native-access=ALL-UNNAMED -cp "../bin:../src:*:MacSilicon/swt.jar" -Djava.library.path=MacSilicon/lib com.cubaix.TDenlive.TDenlive
```

On Linux, drop `-XstartOnFirstThread`, use the `Linux/` jar and libs, and set `GTK_OVERLAY_SCROLLING=0`. The README has the per-platform variants.

`./Install-Dev.sh` downloads two kinds of binaries into gitignored folders:
- ffmpeg into `distrib/ffmpeg/`. The binaries are not in Git or in the jar because they are 60 to 180 MB each. The files are named `ffmpeg-<os.arch><suffix>`: `ffmpeg-amd64`, `ffmpeg-amd64.exe`, `ffmpeg-x86_64-osx`, `ffmpeg-aarch64-osx`. `SOURCES.txt` records where each one came from.
- A Java 27 JRE per config into `JVMs/<config>/`: Temurin, or Azul Zulu for MacIntel because Temurin has no macOS x64 build.
- A Java 27 JDK for the host machine into `JVMs/JDK/`.
- JavaFX for the Linux config into `distrib/Linux/javafx/` (see Demos below).

Its options are config arguments, `--ffmpeg-only`, `--jvm-only`, `--jdk-only` or `--javafx-only`, and `-f` to re-download the latest releases.

`run_3De.sh` and `build_delivery.sh` don't trust the default `javac` / `java` (a Linux machine may have javac 8 and java 25): `find_jdk.sh` (sourced) looks for a Java 27+ tool in `JAVA_HOME`, on the `PATH`, in `JVMs/JDK/`, then among the installed JDKs (`/usr/lib/jvm`, `/Library/Java/JavaVirtualMachines`...). `run_3De.sh` compiles with that JDK but runs with the JRE of the delivery of the host config, `JVMs/<config>/bin/java`, and only falls back to `find_jdk.sh` when it is missing.

`./build_delivery.sh [config...]` builds the deliveries:
- It compiles into `delivery/build/`, copying the resources next to the classes, then builds the jar.
- Each config gets a self-contained `delivery/3Denlive<config>.tar.gz`, except Windows, which gets a `.zip`. The archive contains the jars, SWT, `lumas/`, `frames/`, the platform's `ffmpeg/`, `jre/`, `javafx/` for Linux and the launcher.
- The launchers (`distrib/<config>/3Denlive.sh`, `Win-x64/3Denlive.bat`) use `./jre` when it is present, and the system java otherwise.
- PPC64le has no bundled ffmpeg and uses the system one.

`src/demo/DemoLogo.zip` goes into the jar like the other resources: at startup, `TDenlive.installDemo()` unzips its `DemoLogo/` folder into `~/3Denlive/DemoLogo_<version>/` (version of `VERSION.txt`) if `DemoLogo_<version>/DemoLogo.3De` does not exist (the files already there are kept; the media paths of the project are relative).

`distrib/3Denlive.jar` is tracked in Git but not regenerated by any script.

## Version

The version lives in `src/com/cubaix/TDenlive/VERSION.txt` (one line, `X.Y.Z`). `TDenlive.TDeVersion` reads it with `getResourceAsStream`, and `build_delivery.sh` reads it for its output. **After any code change, increment the last number (Z) by 1**, once per set of changes, not once per file.

## Architecture

All code lives in `com.cubaix.TDenlive`, with a vendored Nebula `TableCombo` widget under `org.eclipse.nebula`.

- **`TDenlive`** is the app root. A single instance is passed to almost every constructor as `tde`/`aTDe`, and it holds `config` (`TDConfig`), `gui` (`TDeGUI`), `mediaList`, `timeLineStack` and `selected`. It also writes and reads the project file.
- **Persistence**: projects (`<3De>…</3De>`) and the user config (`~/3Denlive/3De.conf`) are hand-built XML. They are written by appending to a `StringBuffer` in each class's `saveProject(StringBuffer)`. They are read with the custom `xml.XmlMinimalParser`, which turns the file into a flat `Vector<XmlObject>`. Each class's `openProject(Vector<XmlObject> aOs, int o)` consumes tags from index `o` and returns the new index; a tag's text is in `aOs.elementAt(++o).text`. Follow this cursor pattern for any new persisted field, and keep save and load symmetric.
- **Project folder**: "Save" opens `GUI/SaveProjectGUI` (name, folder typed or chosen with a `DirectoryDialog`, "create a new folder for the project" checkbox, checked for a never saved project: `<folder>/<name>/<name>.3De`), not a native save panel. When the project folder changes (and not when saving before quitting), `TDeGUI.offerGather()` proposes to move, copy or leave the media files outside it: `utils.ProjectFiles.relocate()` puts them at the root of the project folder (`name_2.ext` if taken), with their computed depth maps, WorkCache work copy and sound cache renamed for the new path (`AudioReader.cacheFileFor()`; a move that fails becomes a copy), rewrites the paths in the project XML, saves it and opens the project again. Adding a file from outside the folder of a saved project (`OpenMediaGUI.askCopy()`) proposes to copy it there (`ProjectFiles.importFile()`, in the loading thread; a copy with the same name, size and date is reused).
- **Media model (`medias/`)**: `Media` (abstract, extends `GUI.Drawable`) has these subclasses:
  - `StereoImage`, with `StereoMovie`, `StereoSvg` and `ColorBck` extending it. `utils.MpoReader` handles MPO stereo photos.
  - `Clip`, a placement of a media on a timeline. It owns an ordered `processors` list and links to its twin clips.
  - `VideoTimeLine` and `AudioTimeLine`.
  - `TimeLineStack`, which composes the timelines.
  - `ShapesMedia` (shapes clip, created from the media list toolbar with the `GUI/ShapesClipGUI` popup) holds the initial vector shapes (`shapes.Shape`, frame coordinates 0..1, a depth = L/R parallax). Its clips get the mandatory `processors.Shapes` (undeletable, unmovable, right after the `TimeController`): every key holds all the shapes (same ids and order), interpolated between keys; a deleted shape is only `hidden` from its key on. `shapes.ShapesEditor` is the shared vector editor (popup canvas, shown in the monitor's view mode: `Mixer.copyMode()` + `Mixer.mix2Swt()` on the left/right renders, same per-eye views; and `MonitorGUI` overlay when the selected clip has `Shapes`: an edit at a time without a key adds one there); `GUI/ShapesPanel` holds its tools and properties. On the monitor, the editor views (`ShapesEditor.View`) map the shapes through the geometry of the active processors after `Shapes` (`Shapes.getChainTransform()` composes `Processor.getGeometry()`: affine, per eye; only `StereoAligner`, via its shared `computeGeometry()`, and `Placer` move the image, the others count as identity). When the mixer shows both eyes on one image (anaglyph...), each frame has a left and a right view (same `group`): a click picks the nearest handle or shape image of either eye, the handles of a shape shifted in depth are drawn for both eyes (red / cyan), once when they coincide.
  - Subtitles: `processors.Subtitles` ("Video" folder of the library) extends `Shapes` with a single text shape (keys like `Shapes`; before interpolating, `interpolate()` gives every key the text of the time, so that the line height is interpolated), drawn over any clip in the frame of the montage (output at the montage size, image at its top left corner). Its cues come from a `.srt` / `.vtt` file read by `utils.SubtitleFile` (file dialog opened when the processor is added, "Add a subtitle" button of `GUI/processors/SubtitlesGUI`) and are saved in the project (`<cue>start;end;text</cue>`). The text at a time is the cue of the media time (`time - startTimeMS + shiftTimeMS`; the last started among overlapping cues), set with `Shape.setTextKeepLines()`: same line height, the middle of the bottom side stays, so texts of several lines grow upward. `ShapesPanel` in single text mode (no tools) edits its style; its text field changes the current cue.
  - Text fonts go with the project: `shapes.ProjectFonts` copies, at the save, the files of the families named by the `<fontName>` tags of the project XML (all their styles, found among the fonts already registered from a project, else in the system font folders) into `Fonts/<project>/` next to the `.3De`, removes the unused ones, registers them at the opening, and `packProject` zips them. Roboto (embedded) and the Java logical fonts are not copied.
  - Each media row of the media list has a trash button (drawn by `MediaList.drawSwt()`, hit by `trashAt()`; `MediaListGUI.trashMedia()`): if the media is used by clips of the time lines (`TimeLineStack.clipsOf()`) or as the depth map of a `DepthmapStereo` key (`depthUsesOf()`), a confirmation first; then `TimeLineStack.releaseMedia()` removes its clips (with their twins) and those depth references, and `MediaList.removeMedia()` removes it.
  - Timeline clips draw a film strip: `Media.getThumbAwtAt(time)`. For `StereoMovie` it comes from `ffmpeg.VideoThumbnailer` (one background ffmpeg run per video, one video at a time); the single `buildThumb()` image is only the media list thumbnail and is no longer rebuilt at each frame.
- **Processors (`processors/`)**: each effect extends `Processor` and implements `process2Swt(...)` for the on-screen preview, `process2Awt(...)` for full-quality rendering, and `openProject`/`saveProject`. Keyframed parameters use the `getNbKeys`/`addKeyGT`/... methods. Key times are relative to `Clip.getKeysOriginMS()` = `startTimeMS - keysShiftMS`, not to the clip start: the second part of a clip cut with the scissors (`Clip.cutAt`, "Cut at position" button right of "Delete clip" in the clip panel, `TimeControllerGUI`) keeps the same keys with `keysShiftMS` = the cut offset, so keys may lie before the start or after the end of a clip. In the GUIs, a parameter setter takes its key from `LabelKeyFrame.editKey()`: the key exactly at the time cursor, else a new interpolated key inserted there (the widgets are refreshed from it afterwards with `asyncExec`). This is the automatic mode. Above the K row of each processor (`LabelKeyFrame`), a "Select" button adds to the selection the key at the time cursor, else the nearest one on its left (`Processor.selectKeyGT()`; `selectedKeyTimes`, by key time, the last selected being the main one), drawn as yellow squares by `KeyFrame`; "Unselect" clears it and goes back to the automatic mode (`isAutoKey()` = no selected key). The selection is saved by `Clip` as `<ProcSelKeys>t1;t2</ProcSelKeys>` after the processor (the old `<ProcAutoKey>` is ignored). In automatic mode the widgets show the values interpolated at the cursor (`LabelKeyFrame.displayKey()` → `Processor.setDisplayKeyGT()` + index `Processor.DISPLAY_KEY`, read by the getters through each processor's `key()`; the real keys are untouched); with a selection they show the main selected key. The GUIs change a parameter with `lkf.edit(aEK -> proc.setX(aEK, v))`: the same value goes to all the selected keys, else to `editKey()`. `Shapes.manualKey()` (main selected key) is what the shapes editor edits then, and `Shapes.syncSelectedKeys()` (editor listener) copies each shape changed in it into the other selected keys; its clicks hit the shapes where they are drawn (`ShapesEditor.Source.getDisplayedShapes()`, interpolated; the edited key shape of the same id is moved), plus the outline of the selected shape at its key place; only the selected shape has handles. Every `Clip` starts with a `TimeController` and a `StereoAligner`. `Mixer` subclasses (`AnaMixer`, `SbsMixer`) produce the anaglyph or side-by-side output, and `Renderer` sends frame pairs to the encoder. `Scripter` runs user BeanShell (`bsh`) scripts.
- **Depth maps (`depth/`)**: `Depthmap` (2D + depth map) and `DepthmapStereo` can compute their depth maps with Depth Anything V2.
  - **When**: when one of them is added from the library (`ProcessorLibGUI`) to a clip, `GUI/DepthmapConvertGUI` behaves as follows:
    - it uses the existing `_3eDepthMap` files of the media without asking;
    - otherwise, when the clip has no depth map, it proposes the computation (`DepthConverter.hasDepthmap()`: not a single 2D file, and a gray right view with a non-gray left view);
    - the button of the processors' GUIs computes them again (`aForce`).
  - **Placement**: a clip has at most one depth processor (`Clip.getDepthProcessor()`; adding a second one is refused). It is always first after the `TimeController` (and `Shapes`), unmovable: see `Clip.placeDepthProcessor()`, also applied at the loading.
  - **Models**: the user chooses the model in `DepthModel`: Small is Apache-2.0, Large is CC-BY-NC-4.0.
  - **GPU or CPU**: both models run on the GPU when one has at least `DepthModel.gpuMemory` free (1.5 / 5 GB, from the peak footprints measured with WebGPU).
    - Only two GPU providers exist in the Java builds of ONNX Runtime 1.31: WebGPU/Metal, in the standard jar for macOS only, and CUDA, in the `onnxruntime_gpu` jar (Windows x64 / Linux x64, 385 MB, needs CUDA 12 + cuDNN 9 installed). `DepthEstimator.useGpuRuntime()` downloads the CUDA jar instead of the standard one when `nvidia-smi` is found. The other Windows / Linux machines, and the integrated Intel / AMD GPUs, compute on the CPU.
    - `DepthEstimator.bestGpu()` takes the NVIDIA GPU with the most free memory (`nvidia-smi` index, passed to `addCUDA`; it matches the CUDA order with `CUDA_DEVICE_ORDER=PCI_BUS_ID` or identical cards). When all of them are full, the CPU is used. On macOS (unified memory), the free memory comes from the free + reclaimable pages of `vm_stat`, capped at 3/4 of the RAM.
    - The GPU providers are tried in this order: CUDA, then WebGPU. If CUDA fails (`CPU_REASON_CUDA`, usually CUDA / cuDNN missing) or the GPU fails during the run, the estimator goes on with the CPU (`cpuReason`).
    - The progress window says whether the computation runs on the GPU or the CPU and why, but never the provider name ("WebGPU" suggests that data leaves the computer).
    - CoreML is not used: on Apple Silicon it is 3 to 15× slower than the CPU on these models, whereas WebGPU is about 5× faster.
  - **Child process**: the public `DepthEstimator` constructor starts a child JVM (`DepthEstimator.main()`, same java and classpath, `-Xmx2G`, binary protocol on stdin / stdout, logs on stderr) that loads the model with the package constructor `DepthEstimator(dir, model, true)`; `estimate()` sends the image resized to the model size and reads the depth back; `close()` stops the child. Reason: ONNX Runtime keeps its native memory (about 2 GB for Large, CPU or WebGPU) after its session is closed, until the end of the process. The Python generators are child processes too, killed by a shutdown hook if the application quits. The launchers add `-XX:G1PeriodicGCInterval=30000` so that the Java heap given back after a big job (video decoding...) is returned to the system when idle.
  - **Downloads**: at the first use, the ONNX models (Hugging Face `onnx-community/depth-anything-v2-*`) and the ONNX Runtime jar (Maven Central, standard or CUDA build) are downloaded into `~/3Denlive/Models/`. The jar is not in `distrib/`, the classpath or the deliveries: `DepthEstimator` loads it with its own `URLClassLoader` and calls it by reflection. Its natives exist only for Windows x64, Linux x64/arm64 and macOS arm64 (`isPlatformSupported()`).
  - **Files**: `DepthConverter` writes one file per source file, next to it: `<name>_3eDepthMap.png`, or `.mp4` without sound (`ComputedDepthmap.depthPath()`). It falls back to the WorkCache when the folder is read-only.
    - The file keeps the stereo layout of the source: a side-by-side source gives a side-by-side map, and an MPO gives a parallel PNG.
    - All the views are computed, whatever the processor. White is front, so `blackIsFront` is set to false.
    - For video, it decodes with `FfmpegDecoder`, smooths the depth levels across frames, and encodes gray frames with `ffmpeg.FfmpegRawEncoder`.
    - After a new computation, `ComputedDepthmap.forget()` drops the loaded medias and the video work copy.
  - **Attachment**: the maps are not added to the media list. `depth.ComputedDepthmap` (the processor's `computed` field) finds the files back from the clip's media (`find()`).
    - It loads them into a media cached by file name, in the source's layout. A video gets its work copy in the WorkCache like any other, and `StereoMovie.noSound`.
    - It gives the clip a paired clip with `followsOrientation`, which copies the rotation and anamorphosis of the clip's media in `Clip.reBuild`.
    - Processors only save `<computedDepth>true</computedDepth>`.
    - `TDenlive.packProject` adds the files next to the packed medias, named after the packed name. "Save as" copies those in the WorkCache.
    - `Processor.removed()` (called by `Clip.removeProcessor`) releases the paired clip.
  - **Depth map used**: `Depthmap` uses the left computed map if any, else the right view of the media (2D + depth map). `DepthmapStereo` uses the key's own depth media if any, else the computed maps (shown as "(computed)" in its combo), one per view. The maps are resized to the views with `ImageUtils.fitTo`.
  - **Mix (M)**: a keyed parameter `m` (0..1, slider M 0..100, `<m>` tag) of both processors mixes the depth map on the source before the conversion (`Depthmap.mixDepth()`: colors only, the source alpha is kept): 0 = the source as before, 1 = the depth map converted to stereo instead of the image.
  - **Display**: the "Show the depth map" checkbox, right of the compute button, sets `showDepth` (not saved). Outside the RENDER mode, the processor then outputs the depth maps instead of its result.
- **3D models (`model3d/`)**: the cube icon button right of the shapes clip button (`MediaListControlGUI`) opens `GUI/Model3DGUI`, a mini modeler.
  - `Model3D` = nodes (`Object3D`: cube, sphere, cylinder, cone, torus, pyramid, plane, tube, extruded text, group), an orbit camera (target, yaw, pitch, distance, vertical fov), `depth` (eye separation / distance) and `spin` (turntable, °/s around the vertical axis of the target). `nextId()` never gives back the id of a deleted node (`lastId`, saved): the clip keys are by id.
  - Hierarchy: `Object3D.parent` = id of a `GROUP` node (no mesh); local = R·S·mesh + position (R = Rz·Ry·Rx, degrees), `Model3D.world()` composes the chain, `setWorld()` writes a world transform back into the local one (`Math3D.decompose()`, a shear is lost). `group()` / `ungroup()` keep the world transforms; `remove()` / `duplicate()` work on subtrees.
  - Text: `Mesh3D.text()` (cached) builds the mesh from the glyph outlines (`ShapeText` fonts): front / back faces cut into horizontal trapezoids between the edges (non zero winding), side walls with smoothed normals on the curves; a line is 1 high, `extrusion` = thickness. The font is saved in a `<fontName>` tag, so `ProjectFonts` copies it with the project.
  - `Camera3D`: eyes shifted along the right axis, parallel axes with an off-axis shift, zero parallax at the target. `Renderer3D` is a software rasterizer (z-buffer in 1/z, Gouraud, light tied to the center camera so both eyes are shaded alike, supersampling, transparent background; editor options: grid, id buffer for the picking, selection outline).
  - `GUI/Model3DView` is the interactive view shared by the modeler and the clip panel (`Source`: the model, the camera holder, `beginChange()` / `changed()`): a click selects the group of the root level (Cmd / Ctrl: the object itself; a click on a node already selected, or inside it, keeps that node: an object chosen inside a group stays the one edited), tools Move / Rotate / Scale with gizmo handles (world axes, axes of the main object to scale), X / Y / Z constraint, snapping, done in the world on the nodes not below another selected one. The modeler adds the tree of the nodes, numeric fields (local, in the group; the main node takes the value, the others the same change), text properties, group / ungroup, its own undo stack (the view is not part of it), stereo preview in the monitor's mode (view only).
  - `medias.Model3DMedia` (extends `StereoImage`, `<Model3DMedia>` with a `<Model3D>` inside) renders both eyes at the output size; with a `spin` the image follows the media time.
  - Its clips get the mandatory `processors.Objects3D` (undeletable, unmovable, right after the `TimeController`, added at the loading to older clips; GUI `GUI/processors/Objects3DGUI`: "Edit the 3D model" button at the top, K row, compact `Model3DView`, tree, fields, Reset). A key holds a `Pose` per node relative to the model of the media (position + d, rotation q·R with a quaternion, scale × k; none = no change), so that the model edited later still applies; interpolation linear, slerp for the rotations. The view edits `modelForKey()` of the main selected key, else the model at the time cursor; a change goes to the selected keys, else to `LabelKeyFrame.editKey()`. When all the poses are identity at a time, the image of the media is kept, else the processor renders the animated model.
- **Edit buttons of the media list**: the medias made in the application (`MediaList.isEditable()`: `ShapesMedia`, `Model3DMedia`) have a pencil left of the trash (`editAt()`, `MediaListGUI.editMedia()`). The shapes editor gets the shapes (new ids above those of the clips, `Shapes.maxShapeId()`), then `Shapes.mediaShapesChanged()` updates the keys of the clips: removed and added shapes everywhere, a changed shape replaced only in the keys where it is still as in the media. A 3D model is reopened in the modeler; its clips follow (relative poses).
- **AI clips (`ai/`)**: the "AI" / "IA" text button right of the 3D model button (`MediaListControlGUI`) opens `GUI/AiClipGUI`, whose form starts with a Video / Music / Sound effects selector (`KINDS`, `StackLayout`, one panel each, the kind last chosen `TDConfig.aiKind`, music the first time; not the video when it is not possible here). Each panel has two columns (description + its own models + where it runs on the left; prompt, examples, duration, downloads on the right) and only the models of its kind (`createModelChoice()`): the one advised for the hardware (largest that fits in the free GPU memory, `DepthEstimator.bestGpu()`) in bold and selected, unless the user chose another one (`TDConfig.aiVideoModel` / `aiMusicModel` / `aiSfxModel`, "" = advised). `ai.PythonAI` is the base of the generators: the shared Python environment (uv, `Models/Python/wan-env`, name kept), the script protocol (`runScript()`: `STATUS`, `STEP`, `PEAK`, `DONE`, `ERROR`, other lines to `handleLine()`), the downloads (`downloadFiles()`), the cancel.
  - **Sound**: `ai.SoundGenerator` with `SoundGenerator.Model`s by kind (`models(kind)`, `defaultModel(kind)`): music = MusicGen Small / Medium / Large (`musicgen_generate.py`, transformers `MusicgenForConditionalGeneration`, CC-BY-NC-4.0, Medium and Large only as `.bin`, 32 kHz, at most 30 s); sound effects = AudioLDM 2 / AudioLDM 2 Large (`audioldm2_generate.py`, diffusers `AudioLDM2Pipeline`, cvssp/audioldm2 and audioldm2-large, same files but the UNet, CC-BY-NC-SA-4.0, 16 kHz, at most 20 s, `SFX_STEPS`; the script replaces `generate_language_model()`, whose GPT-2 loop calls private methods removed from transformers 5). Third sound effects model: MOSS-SoundEffect v2.0 (`SoundGenerator.MOSS`, OpenMOSS-Team, Apache-2.0, DiT 1.3 B + Qwen3 1.7 B text encoder + DAC VAE, 48 kHz, at most 30 s, always denoises 30 s; `moss_soundeffect_generate.py`): its inference code (`moss_soundeffect_v2` of github.com/OpenMOSS/MOSS-TTS at `MOSS_COMMIT`, `MOSS_CODE_FILES`, no training code) is downloaded into `Models/MOSS-SoundEffect-v2.0/code/`, and it runs in its own environment `Models/Python/moss-env` (`MOSS_ENV`, the pinned versions of its pyproject: transformers 4.57, diffusers 0.37). `PythonAI.Env` (name, version, packages; `SHARED` = `wan-env`) and `PythonAI.env()` / `Model.env` choose the environment. The script disables the torch.package loading of audiotools (its VAE `.pth` is a plain state dict, loaded with `weights_only`) and replaces `sinusoidal_embedding_1d` (float64, missing on MPS) by the same computation on the CPU, and makes the RoPE frequencies complex64 (`precompute_freqs_cis`, complex128 otherwise, also missing on MPS). Its memory needs are estimates. Each model goes into `Models/<dir>/` with its file list and the memory it needs (NVIDIA fp16 / Apple Silicon fp32 / CPU RAM; measured peaks on Apple Silicon: MusicGen Small 4 GB, AudioLDM 2 6.4 GB, Large 7.9 GB), shown in the form with a note per model (`AI.Model<id letters>Note`). Where it runs: `cpuReason()` gives `--device cpu` without GPU or when the NVIDIA GPU lacks free memory. Output `AI/<name>.wav` (default `AI_Music_<date>` / `AI_Sfx_<date>`) + prompt, added with `MediaList.loadAudio()` once validated in the result window (see below). fp16 on CUDA, fp32 on MPS (fp16 measured slower there, no memory gain) and CPU. The MusicGen progress comes from a `LogitsProcessor` (transformers 5 no longer passes the streamer to the sampling loop).
  - **Example prompts**: `res/ai/ai_prompts.txt`, `kind|Category/Subcategory|BPM|Name|prompt` (kind `video` / `music` / `sfx`, 1000 each, about 50 subcategories per kind; BPM empty but for the music, also at the end of the English music prompts; the video prompts stay simple for the 5B model: one subject, one action, a place, a light, a camera movement). `AiClipGUI.createExamples(panel, kind)` shows, in the panel of that kind, an SWT `Tree` category > subcategory (a subcategory named as its category is not a level) > prompts (music by tempo), with counts; names translated by `AI.PromptCat<letters of the name>`. Translations of the examples: `res/ai/ai_prompts_<LNG>.txt` (`kind|English name|name|description`, key = kind + English name; `FR` has all 3000), loaded by `soundExamples(tde.config.lng)`: the tree shows the translated name and description, but a click fills in the English prompt (the language of the models) and the translated name. Each panel has a name field (`createNameField()`): the generated file is `AI/<name>.mp4|.wav` (`fileBase()`: characters not allowed in a file name replaced; `name_2`... when taken; empty: `AI_<date>`), so the media list shows that name.
  - **Result window**: at the end of a generation, `GUI/AiResultGUI` plays the result after a click on Play, never automatically (the video in a loop, frames decoded by ffmpeg as a BMP pipe at 560 px; the WAV with a `javax.sound` `Clip`; Play / Pause, the bar moves the position), then "Add to the media list" (loaded in a thread), "Generate again" (files deleted, `AiClipGUI.again()`: the form with the same kind, prompt, name and duration) or "Discard" (files deleted; closing the window asks first). `AiClipGUI.running` stays true until then.
  - **Video**: the transformer of Wan comes in `WanGenerator.Variant`s Q8_0 / Q6_K / Q4_K_M (GGUF of QuantStack, the other files shared; GPU memory 10 / 9 / 8 GB: only the transformer stage shrinks, `defaultVariant()`). A form (GPU memory warning, prompt, duration 1 to 5 s = at most 121 frames at 24 fps, 1280x704 or 704x1280 for a portrait output), then a progress window with an animated preview. `ai.WanGenerator` generates with Wan2.2-TI2V-5B through the Python script `res/ai/wan_generate.py` (copied next to the model at each run), with no Python needed beforehand:
  - at the first use it downloads uv (pinned `UV_VERSION`), which installs Python 3.12 and PyTorch (`--torch-backend=auto`: CUDA build for the NVIDIA driver) + diffusers into `~/3Denlive/Models/Python/` (`ENV_VERSION` marker: increment it when `PACKAGES` change), and the model files into `Models/Wan2.2-TI2V-5B/` (diffusers repo without its bf16 transformer, plus the GGUF Q8_0 transformer of `QuantStack/Wan2.2-TI2V-5B-GGUF`), with `depth.Downloader`;
  - the script loads one model at a time on the GPU: text encoder in 8 bits (bitsandbytes, NVIDIA; bf16 on the CPU otherwise), then the GGUF transformer, then the fp32 VAE with tiled decoding. It needs CUDA (NVIDIA, Windows / Linux x64) or MPS (Apple Silicon); no CPU fallback. It reports on stdout (`STATUS`, `STEP`, `PREVIEW`, `PEAK` = real GPU memory peak per stage, logged, `DONE`, `ERROR OOM|NOGPU|...`);
  - optional reference image (form: Choose / Remove, thumbnail; the video orientation follows it): `--image`, cropped to the video ratio and encoded by the VAE (on the GPU before the transformer is loaded) as the first latent frame, kept during the denoising (timestep 0 for its tokens, as `WanImageToVideoPipeline` with `expand_timesteps`). The denoising loop is the script's own (CFG, UniPC), not a diffusers pipeline, so that the VAE stays on the CPU meanwhile;
  - preview: at each step the predicted clean latents (x0 = x_t - sigma * v) mapped to RGB with ComfyUI's Wan2.2 latent factors, frames side by side in one PNG;
  - the 2D video (ffmpeg H.264, no sound) and its prompt (`.txt`) go into `AI/` next to the project (`~/3Denlive/AI` before the first save), and the video, once validated in the result window, is added to the media list as a flat media.
- **Audio**: a video clip carries its own sound, drawn as a bar under its film strip (`VideoTimeLine.SOUND_BAR_H`). The `AudioTimeLine`s hold sound-only clips (`AudioMedia`); like the video lines, they are drawn from the last added (top) down to A1 (bottom), below the video lines, and a clip moved "up" goes to the next index. Each line has `isActive` (checkbox: images and sound) and, for video lines, `soundSource`: left video (default), right video (the right file of a two-file media, else the single one) or mute. It is chosen in a popup menu of the sound icon left of the checkbox (`VideoTimeLine.chooseSoundSource()`), which is crossed out when muted. Below them, two yellow arrows (`arrowUp.png` / `arrowDown.png`, not drawn on the top / bottom line of its kind) move the whole line in its stack (`TimeLineStack.moveLine()`, lines named again V1.. / A1..). Both are saved in the project and used by play and rendering; `<soundMuted>` of old projects is still read. The line sets `Clip.soundRight` before mixing or drawing, and `Clip.getSoundReader()` → `Media.getAudioReader(boolean)` reads the right file's sound only in that case: by default the sound is always that of the left video. `Clip.soundOn` mutes one clip (off for the copies made by "duplicate to above line"). Projects of 1.0.7 had the sound as an audio *twin* clip: `TimeLineStack.mergeSoundTwins()` folds it back into the video clip on load.
  - `ffmpeg.AudioReader` decodes a file's first audio stream once into a raw PCM cache (s16le stereo 48 kHz) in `TDenlive.getWorkCacheDir()` = `WorkCache/` sub folder of the project folder, shared by the projects of that folder (`~/3Denlive/WorkCache` before the first save; caches are copied on save; the files of an old `<project>_3De_AudioCache` are moved into it), read by random access, plus a peak envelope for the waveforms. `Media.getAudioReader()` gives it (`StereoMovie`, `AudioMedia`; `null` for still images).
  - `audio.AudioMixer` mixes all the lines (`VideoTimeLine.mixAudio` → `Clip.mixAudio`: processors' `processAudio(...)`, then fades). `audio.AudioPlayer` plays it with `javax.sound` and is the clock of the play loops when there is sound; `RendererGUI` mixes a temporary WAV that `FfmpegEncoder` muxes (AAC in mp4, none for image sequences).
  - Sound processors (`Volume`) return `true` from `Processor.isAudio()` and are listed in `ProcessorLibGUI.AUDIO_PROCESSORS`: allowed on any clip with a sound; image processors are refused on audio-line clips.
  - ffmpeg BMP pipes are read with `Ffmpeg.readBmp()` (cut by the header size): `ImageIO.read` alone misreads concatenated BMPs whose row width is not a multiple of 4.
- **Processing modes**: `TDConfig.PROCESSING_MODE_{WORK,FULLSCREEN,RENDER,AUTOALIGN}`. Each mode has its own resolution/HDR settings, which is why processors receive a mode argument.
- **Adding a processor** means adding it by name string in several places that are not tied together by any registry:
  1. the class in `processors/`;
  2. the GUI in `GUI/processors/` (extends `ProcessorGUI`);
  3. `Clip.openProjectProcessors` (XML tag → instance);
  4. `Clip.addProcessor` (name → instance);
  5. `GUI/ProcessorsGUI` (class name → GUI);
  6. `GUI/ProcessorLibGUI` (library tree entry);
  7. a label in both `res/lngs/EN.xml` and `res/lngs/FR.xml`.
- **Undo / redo (`GUI/History`)**: no command objects. After each interaction (display filters: mouse up, key up, selection, focus out, then `IDLE_MS` without event; a mouse down first records the pending change; a `POLL_MS` timer catches background changes), `tde.projectXml()` plus the processors' `isActive` (not saved in projects) is compared to the current state; a difference is a new state (at most 100 operations). A drag gives only its start and end (nothing while a button is down; the button counts as released when the clicked control is disposed, e.g. a panel rebuilt by its click, or at a mouse move without button). Each state keeps its medias with their XML (an unchanged media object is reused at restore, not reloaded), a key expression from `describe()` (XML diff: media, clip, processor, line... `History.*` language entries, shown in the buttons' help) and the views before / after the change (`ViewState`: time cursor, selection by UIDs, monitor media and mixer, processors panel and expanded processors, shapes editor selection and tool, scrolling). Restore = new `mediaList`/timeline vectors parsed from the XML, then the views; undo applies the `viewBefore` of the undone state, redo the `viewAfter`. Buttons right of Render (after a button-wide space), Ctrl+Z / Shift+Ctrl+Z (Cmd on macOS) in the main window. Opening a project sets `history.loading` and `reset()`s it at the end.
- **Demos**: the first button of the main toolbar (`demos.png`, clapperboard) shows the demos page of the web site (`WebBrowserGUI.demosURL()`: `demos/index.php` in French, else `demos/en.php`) in the central panel. `TDeGUI.setMultiMonitorPanel(kind, url)` keeps the browser and the monitor once created and only switches which one is visible (`GridData.exclude`), so the monitor keeps its state. A click on a `3denlive.com/demos/*.zip` link ("Project") is intercepted by the browser's `LocationListener` (`DemoProjectGUI.isDemoZip()`); at each page load, `WebBrowserGUI.DEMO_BUTTONS_JS` (run with `Browser.execute()`) restyles those links as purple buttons with a download sign: `GUI/DemoProjectGUI` asks to save a modified montage, downloads the zip into `~/3Denlive/Demos/<name>.zip` (progress window, cancel), unzips it into `~/3Denlive/Demos/<name>/` (a leading `<name>/` folder is not doubled, nothing outside it) and opens its `.3De`; a demo already there is opened again or downloaded again on request. When SWT has no browser (Linux without WebKitGTK: `new Browser` throws), `WebBrowserGUI` uses `GUI/FxBrowser`, the WebKit of JavaFX, so that the Linux delivery stays self-contained:
  - JavaFX (Gluon SDK `JAVAFX_VERSION` of `Install-Dev.sh`: base, graphics, controls, media, web, `javafx-swt`, `jdk.jsobject` + all the `.so`) goes into `distrib/Linux/javafx/` (gitignored) and `javafx/` of the Linux delivery. It is not on the classpath: `FxBrowser` loads it with its own `URLClassLoader` (parent: the application loader, for SWT) and calls it by reflection (methods taken on the public JavaFX types, listeners as `Proxy`), so nothing JavaFX is needed to compile or on the other platforms. The natives are found next to the jars.
  - The `WebView` is in an SWT `FXCanvas` (the SWT thread is the JavaFX thread; `Platform.setImplicitExit(false)` for the rebuilt window contents). JavaFX needs X11: the Linux launchers (`3Denlive.sh`, `run_3De.sh`, `launch.json`) set `GDK_BACKEND=x11` unless already set.
  - At each page load it runs `res/html/javafx_fixes.js`, then `DEMO_BUTTONS_JS`: a seek when a video starts playing (a video moved while paused stays stuck otherwise), the `multiply` / `lighter` canvas operations of the stereo player's 2D fallback (no WebGL) done on the pixels, `requestAnimationFrame` at 30 fps, and the clicks on `.zip` links sent to the application as an `alert("TDE-ZIP:<url>")` (`setOnAlert`), opened by `DemoProjectGUI` (other zips: system browser). Failed load: `errorPage()`. The cookies go through `java.net.CookieHandler`.
  - Its videos use the `libavcodec` of the system (none: the pages work, not their videos).

  Without either (no WebKitGTK nor JavaFX), `WebBrowserGUI` shows a message (`Web.*`) and a button that opens the page with `BrowserControl.openURL()`; a page asked later (demos button) goes straight to the system browser, so the demo zips are not intercepted.
- **Monitor ruler and play buttons**: `GUI/MonitorRulerGUI`, between the monitor and the player buttons, shows the whole duration of the media shown (the montage from 0 to the end of its last clip, or the library media played alone) fitted to its width, with the cursor of the time lines (pink inverted triangle); a click / drag moves the time, a play in progress goes on from the release. It is redrawn by `MonitorGUI.redraw()` / `setMedia()` and `TimeLineStackGUI.redraw()`. `PlayerControlGUI`: Stop goes back to the position of the play click; while paused, a second stop button (`stopHere.png`) right of Pause stops at the current position.
- **Hover frames**: `TDeGUI.installHoverFrames()` draws a light gray frame on any `Label`/`CLabel` listening to `SWT.MouseDown` while the mouse is over it; a control with the data `TDeGUI.HOVER_TARGET` frames that control instead (`LabelImageButton`: icon + text, with a 1 px layout margin for the frame).
- **GUI (`GUI/`)**: SWT. `TDeGUI` builds the main window (media list, monitor, timelines, properties and processors panels) and runs the event loop. Calls from worker threads must go through `gui.display.syncExec`/`asyncExec`. Imaging is split between SWT (`*Swt` classes, preview) and AWT `BufferedImage` (`*Awt` classes, rendering). macOS constraints: AWT runs headless (set first thing in `main`), because initializing it from a worker thread otherwise deadlocks with the SWT main thread; and drawing on a control outside a Paint event (`new GC(control)`) is ignored, so store the image and call `redraw()` instead; and a shell without `SWT.TITLE` never becomes the key window, so it gets no keyboard events (hence the titled shell of `FullScreenGUI`, whose title bar is hidden in full screen).
- **Clip selection**: `tde.selected.clips`, the last one being the main clip (processors panel). In `TimeLineStackGUI`, a click on a clip selects it alone, Shift+click adds it (on a selected clip: removes it at the mouse up if not dragged); a click on a clip of a multiple selection keeps it for the drag and selects it alone at the mouse up without a move. A click on the head of a line (V1, A1..., `TimeLineStack.getLineHeadAt()`) selects the line and all its clips (`selectLine()`), Shift+click adds / removes other lines. Dragging a selected clip moves all the selected clips (`TimeLineStack.moveClips()`: same time shift, earliest at 0 at least, sticky edges of any of them with `snapGroupMoveMS()`; the clips of the dragged clip's kind, video / audio, shift by the same number of lines, limited to the stack, the others move only in time). DEL removes all the selected clips. `VideoTimeLine.addMedia()` inserts after the main selected clip.
- **Drag and drop**: a media of the media list dragged onto a line of the time lines (`MediaListGUI` `DragSource`, `TimeLineStackGUI.createDropTarget()`, SWT `TextTransfer` of `MEDIA_DRAG_PREFIX` + UID) becomes a clip at the time of the mouse (`TimeLineStack.dropMedia()`, sticky edges; a sound only on an audio line, a video on an audio line gives its sound), with a preview rectangle while dragging (`setDropPreview()`). A clip dragged on the time lines follows the line under the mouse, of the same kind (`TimeLineStack.moveClipToLine()`).
- **Scrolling panels**: `CanvasPanel` draws its content from `origin` (scroll bars only move `origin` and redraw). With `CanvasPanel(tde, parent, true)` the horizontal bar is a `Slider` in `bottomRow`, so tools can sit on its right: `TimeLineStackGUI` puts the time zoom there (`setZoom()`: `TimeLineStack.pixPerMS` = `DEFAULT_PIX_PER_MS` × 2^(zoom/10), keeping the time cursor in place).
- **i18n**: all UI strings go through `gui.lngs.get("Section.Key")` and are backed by `res/lngs/EN.xml` and `FR.xml`. Add every new key to both files. The languages are listed in `Lngs.LANGUAGES`. The language selector of `SettingsGUI` calls `TDeGUI.setLanguage()`, which rebuilds the main window contents (`rebuildContents()`: the views are kept) and translates the processor names already created (`Lngs.translate()`); open secondary windows other than the settings keep the old language until reopened. Strings read once into long-lived objects need the same treatment.
- **Video I/O (`ffmpeg/`)**: decoding and encoding run an external ffmpeg process. The work preview reads a low resolution copy of each video (`VideoReader`, `FfmpegTranscoder.createWorkCopy`), `StringUtils.path2workingcopy()` = `<WorkCache>/<video>_<key>_3De_WorkCopy.mp4` (an old one next to the video is still used); "Save as" copies them to the new work folder. `Ffmpeg.findFfmpeg()` looks for ffmpeg in this order, and the result is cached:
  1. `/usr/bin/ffmpeg`;
  2. `ffmpeg/ffmpeg-<os.arch><suffix>`, relative to the working directory;
  3. `ffmpeg` on the `PATH`;
  4. `/opt/homebrew/bin` and `/usr/local/bin`.
- **Rendering window (`GUI/RendererGUI`)**: at each counters refresh (`updateStatus()`), an anaglyph thumbnail of the last produced pair with the progress percentage over its bottom right corner. At the end of a video rendering (not an image sequence), `utils.HtmlViewer` writes `<output>.html` next to it, opened in the default browser (`BrowserControl.openFile()`) when the end popup is closed; the instant images ("SaveView", `TDeGUI.saveCurrentImage()`) get `<base>.html` the same way (player on the parallel image, then the left, right, crossed and parallel images under centered `Html.*` titles). The pages embed `res/html/stereoplayer.js`, a copy of https://3denlive.com/stereoplayer.js with image support (`data-type="image"`) and a Canvas 2D fallback when WebGL refuses a `file://` source; they reference the media by file name (same folder).
- **Runtime assets** in `distrib/` (`lumas/` transition masks, `frames/` overlay PNGs) are loaded by relative path. The app must therefore run with `distrib/` as its working directory (the launch scripts `cd` into it).

## Conventions

- Hungarian-ish naming: `a` prefix for parameters and locals (`aPath`, `aOs`), class names without prefix. Tabs for indentation.
- Fixed widget heights (`GridData.heightHint`) are written as `tde.gui.h(n)`, where `n` is the height designed for a 12 px text line. `h()` adds the extra height of the real font (`TDeGUI.textH`, measured at startup; the SWT font size follows the system font). Don't use it for the slider canvases (`ScaleBar`, `KeyFrame`) and their rows (`LabelScale`, `LabelKeyFrame`), which contain no text.
- Errors are generally caught as `Throwable` and printed with `printStackTrace(System.err)`, not propagated.
